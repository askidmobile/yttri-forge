# Q4 decode: сверка консультаций ASTRA xhigh и Opus 5.5 xhigh

Дата: 2026-11-01. Исходная ветка: `main` на `618bf4e0`.

Для продолжения оптимизации были отдельно запущены два read-only исследования:

- `codex exec -m gpt-6-astra -c model_reasoning_effort=xhigh`;
- `claude --print --model claude-opus-5-5 --effort xhigh`.

Обе модели читали текущий код, исследования, CUDA-ядра и llama.cpp как донора. Ни одна из консультаций не меняла репозиторий и не запускала замеры.

## Главный результат сверки

ASTRA нашла дефект корректности, который Opus не обнаружил. В
`flash_decode_paged_gqa_partial` восемь warp'ов считают восемь независимых
Q-heads одной KV-head, но старый эпилог складывал их как части одного softmax и
записывал одинаковый результат всем головам. Поэтому измеренные `13.35` t/s на
128k и `9.92` t/s на 256k относятся к неверному attention-выходу.

Исправление должно идти первым: каждый warp сохраняет свой `m/l/acc` в
`partials[qh]`; combine продолжает объединять только splits одной головы.
`decode_gqa_probe` обязан проверять независимые Q-heads аналитическим тестом.

Исправление проверено на RTX 2080 Ti:

| Проверка | Результат |
|---|---|
| 64 токена, аналитические восемь различных Q | `max|delta|=0.000153` |
| 257 токенов против прежнего scalar-ядра | `max|delta|=0` |
| 131072 KV, scalar | 12.568 ms |
| 131072 KV, исправленный GQA | **2.705 ms** |
| 261900 KV, scalar | 17.675 ms |
| 261900 KV, исправленный GQA | **5.366 ms** |

## Согласованный порядок работ

1. Исправить смешивание Q-heads и добавить per-head parity.
2. Вернуть последовательное `BlockQ8K::from_float` для входа `moe_forward_cpu`.
   Opus связал регрессию `0.014 → 0.30 ms/layer` с восемью Rayon-задачами,
   добавленными в `618bf4e0`.
3. Переснять short/128k/256k с исправленным attention. Старые скорости не
   использовать как baseline.
4. Реализовать opt-in paged GQA decode kernel на `mma.m16n8k8` для
   `head_dim=256`, `n_head/n_kv=8`, сохранив прежний ABI `partials` и combine.
5. Только после профиля критического пути трогать CUDA streams, early CPU
   dispatch и мелкими запусками хвост eager-декода.

## Почему GQA MMA следующий крупный шаг

На 256k старый скалярный GQA kernel занимает около `10 × 5.12 = 51.2 ms/token`.
Это больше всего бюджета llama.cpp (`42.05 ms/token`). Даже мгновенный attention
оставил бы около `20.2 t/s`, поэтому одной оптимизации MoE недостаточно.

RTX 2080 Ti поддерживает Turing tensor cores. Для decode с одним query token
восемь Q-heads одной KV-head дают полезную ширину `m16n8k8`. llama.cpp выбирает
для формы `256/256/8` отдельную Turing MMA конфигурацию. Схему нужно перенести в
собственное Candle-ядро, сохранив paged KV и текущий Rust runtime.

ASTRA дала рабочую цель после исправления:

| Контекст | Сейчас, ms/layer | Цель MMA, ms/layer |
|---|---:|---:|
| 128k | 2.727 | 0.8–1.2 |
| 256k | 5.120 | 1.5–2.2 |

Это проектная оценка, пока не замер. Новый путь запускается только после parity со
скалярным исправленным ядром и отключается через `DECODE_GQA_MMA=0`.

## CPU-MoE

Opus оценил модель короткого decode как
`T = 0.405 + max(L + C(n_cpu), G(n_gpu))` ms/layer. По трём измерениям
`4/4`, `5/3`, `6/2` GPU-ветка читает host-веса примерно на `12 GB/s`, что близко
к практической полосе PCIe 3.0 x16.

До доказанного профиля не повторять:

- дополнительный compute stream для экспертов;
- per-matrix split;
- persistent dispatcher и static row ranges;
- новый expert cache;
- THP, Q4K repack и число Rayon threads.

После GQA parity дешёвый CPU-эксперимент один: убрать Rayon из квантования 2048
float. Если это вернёт `0.014 ms/layer`, upper bound экономии около `11.1
ms/token`, но фактический выигрыш зависит от overlap с GPU5.

Этот эксперимент проверен и отклонён. На коротком HTTP-бенчмарке исправленный
GQA дал `17.09 t/s`; последовательное квантование снизило decode до `15.82
t/s`, а добавление полного Rayon pre-wake на каждом слое — до `14.01 t/s`.
Parity ответа сохранялась во всех трёх вариантах. Rayon остаётся в квантовании:
его восемь задач одновременно прогревают пул перед основным GEMV.

## Проверки и ограничения

- Сначала аналитический тест восьми разных Q, затем реальные короткие
  prefill-tail/decode вызовы, затем teacher-forced logits после 128k/256k.
- Performance gate: три парных прогона short/128k/256k на одном процессе и
  одинаковых prompt/128 output tokens.
- Итоговая цель остаётся `Q4_K_M`, 128k/256k, prefill и decode быстрее
  llama.cpp.
- На 256k одна оптимизация MoE не решает задачу: по обоим меморандумам нужен
  новый tensor-core attention и сокращение остаточного eager/launch хвоста.
