# Сверка ASTRA и Opus по decode на sm75

Дата: 2026-11-01. Исходный `HEAD`: `c54a89d9`.

Для продолжения оптимизации обе модели отдельно прочитали текущий код,
исследования и исходники `llama.cpp`, не меняя репозиторий и не запуская
измерения:

- `codex exec -m gpt-6-astra -c model_reasoning_effort=xhigh`;
- `claude -p --model claude-opus-5-5 --effort xhigh --permission-mode plan`.

Незавершённый Q8 KV diff, находившийся только в
`flash_decode.cu` и `flash_decode_cuda.rs`, по итогам обеих консультаций
удалён: он передавал нулевые указатели масштабов, не поддерживал Q8 в
Turing prefill и не мог самостоятельно закрыть decode gap.

## Измеренный бюджет

| Контекст | yforge, ms/token | llama.cpp, ms/token | Нужно убрать |
|---|---:|---:|---:|
| 128k | 53.82 | 49.21 | 4.61 |
| 256k | 63.90 | 42.05 | 21.85 |

В модели 41 MoE-слой и 10 full-attention слоёв. По микробенчу attention
занимает около 9.66 ms/token на 128k и 18.83 ms/token на 256k. Поэтому
на 256k недостаточно ускорить только attention: даже мгновенное чтение KV
оставляет около 45.07 ms/token.

Существующая формула критического пути после graph/async уже не
калибрована: для `4/4` она предсказывает 53.59 ms/token на short, а
измерено 43.03 ms/token. Числа для выбора нового распределения экспертов
нужно пересчитать после профиля.

## Решение по Q8 KV

Q8 не является следующим шагом. Даже в идеальной модели без стоимости
распаковки он даёт около 20.40 t/s на 128k при цели 20.32 и около
18.33 t/s на 256k при цели 23.78. Реальный путь дополнительно выполняет
`int8 -> float -> half`, умножение и scalar stores, а также требует
изменения prefill.

Вернуться к Q8 можно только при трёх условиях одновременно:

1. F16 attention уже доведён до предела;
2. остаток на 256k до цели не больше примерно 4 ms/token;
3. повторный парный замер подтвердил дефицит, который Q8 способен закрыть.

Отдельная сложность: `PagedKvPool` хранит `k_scale/v_scale` отдельно,
`dispatch_flash_decode_paged` сейчас не умеет их безопасно передавать,
`dispatch_flash_prefill_sm75` требует F16, а `configure_turing` принудительно
выключает Q8.

## Причина текущего attention gap

Главная подтверждённая кодом гипотеза: текущий MMA partial запускает по
одному warp на `16` KV-строк, а загрузчик делает зависимый page lookup и
ограниченное число независимых memory loads. На 256k 256 warp'ов читают
около 536 MB за 1.883 ms, примерно 285 GB/s при паспортных 616 GB/s.
Такой профиль указывает на latency/occupancy, а не на предел DRAM.

`llama.cpp` для формы `DKQ=256, GQA=8` использует 128 threads, 64 KV
строк за итерацию, occupancy 2 и 136 блоков. Поэтому следующий вариант
должен перенести геометрию, а не повторять уже отклонённую замену страничного
lookup без изменения числа независимых загрузок.

## Порядок работ

### D0. Один диагностический профиль

Снять один steady-state профиль на заполненном 256k KV после прогрева
MoE graphs. Нужно разделить:

- сумму attention partial/combine;
- длительность GPU MoE graphs;
- открытое ожидание CPU перед H2D/merge;
- прочие GPU kernels и разрывы host submission.

`MOE_CPU_TIMING` сейчас есть только в синхронной ветке. При необходимости
его счётчики переносятся в async worker; `GPROF=2/3` выключает CUDA graphs
и не подходит для решения об отключении overlap.

### E1. F16 attention: 64 KV строк за softmax-итерацию

В `flash_decode.cu::flash_decode_paged_gqa_mma_partial` добавить opt-in
вариант для `HD=256, GQA=8`:

- четыре warp обрабатывают 64 строки между rescale;
- Q fragments загружаются в registers один раз;
- `chunk` выравнивается так, чтобы tile не пересекал physical page без
  необходимости;
- сохраняются paged layout, `partials` и combine;
- Rust меняет только выбор варианта.

Цель микробенча: не хуже `0.75 ms/layer` на 128k и `1.40 ms/layer` на
256k. Parity должна включать 64/65/127/257 токенов, обе независимые KV
head, все каналы, перемешанную page table, неполные страницы и splits.

Этот вариант отличается от ранее отклонённой замены lookup: тот сохранял
один warp и 16 строк, здесь меняется геометрия и число независимых
загрузок.

### E2. ASYNC CPU-MoE после профиля

Только после E1. Если профиль показывает CPU tail:

- вызывать `moe_forward_cpu` внутри `rayon::scope`, не создавая второй пул;
- проверить C0 через `/dev/cpu_dma_latency` отдельным opt-in;
- выполнить один рассчитанный перенос маршрута (`3 GPU / 5 CPU` при CPU
  tail либо `5 GPU / 3 CPU` при доказанном PCIe-floor), без sweep.

Каждый шаг принимается только при снижении E2E более чем на 2 ms/token.
Если `cpu` не падает ниже примерно 0.45 ms/layer, ребаланс не включается.

До включения async по умолчанию нужно закрыть корректность: worker сейчас
сигнализирует completion flag и при ошибке, поэтому слой может использовать
старый `out`, а ошибка всплывает только следующим вызовом. Ошибка должна
быть fail-closed и проверяться до публикации logits или повторного
использования KV state.

### E3. CUDA graph оставшихся GPU-сегментов

Открыть только если профиль показывает хотя бы 6 ms/token устранимых
разрывов между GPU-операциями. Захватить `attn_norm → DeltaNet/attention →
residual → ffn_norm → router/top-k`, оставив CPU worker и handshake вне
графа. Повторную staging всей block table на каждом токене устранить или
доказать, что она не входит в критический путь.

## Условия приёмки

- Prefill остаётся не ниже 340 t/s на 128k и 305 t/s на 256k.
- Decode должен превысить 20.32 t/s на 128k и 23.78 t/s на 256k.
- Сравнение: один бинарник, одинаковый prompt и состояние KV, 128 output
  tokens, фиксированные NUMA/threads/sampling, три парных прогона.
- Для E1: аналитический probe, перемешанные страницы, `compute-sanitizer`,
  HTTP parity `1, 2, 3, 4, 5, 6, 7,` и teacher-forced logits после
  128k/256k.
- Любая ветка закрывается сразу, если не проходит ранний микробенч или
  parity; длинный E2E для неё не запускается.

## Ограничения

- Измерения 128k для llama.cpp выглядят нелинейно относительно 256k;
  перед финальным выводом baseline нужно переснять тем же бинарником и
  проверить фактическую длину KV.
- Текущий async является opt-in до проверки ошибок, отмены и повторного
  использования слота.
- План не гарантирует победу на 256k: если E1–E3 оставляют больше 4 ms
  до цели, нужен новый архитектурный шаг, а не ещё один локальный tuning.
