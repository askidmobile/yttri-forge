# Исследование: префил на Turing (sm_75), RTX 2080 Ti

**Дата:** 2026-10-30
**Стенд:** RTX 2080 Ti 11 GiB, Xeon 8 vCPU, CUDA 13.4
**Модель:** Ornith-1.5-9B Q4_K_M (36 блоков: 24 DeltaNet + 12 attention)
**Эталон:** llama.cpp build 7df8b87, `llama-bench -p 512 -n 128 -t 36 -r 5-7 -fa 1`

Этот файл — журнал. Он существует, чтобы не перепроверять закрытые гипотезы.

## 1. Текущее состояние

| Метрика | yforge | llama.cpp `-fa 1` | Разрыв |
|---|---:|---:|---:|
| prefill (512 ток) | 2205–2225 tok/s | 2470 tok/s | **−10.5%** |
| generation (128 ток) | 85.2–85.7 tok/s | 85.0 tok/s | **+0.5%** |

Generation достигнута. Prefill — нет. Цель не выполнена.

Профиль тёплого чанка 512 токенов (`TRACE=1`):

```
fwd = 245 ms
  блоки delta (24 слоя) = 169 ms
  блоки attn  (12 слоёв) = 70 ms
```

Разложение (`GPROF=3`):

| Компонент | На слой | На чанк |
|---|---:|---:|
| DeltaNet `proj` (4 матмула) | 1.3 ms | 31 ms |
| DeltaNet `fused` (рекуррентность) | 1.3 ms | 31 ms |
| DeltaNet `head` (ssm_out) | 1.2 ms | 29 ms |
| Attention `sdpa` (ручной F32) | 1.0 ms | 12 ms |
| Attention `proj`/`reshape`/`gate` | 0.4 ms | 5 ms |
| FFN (SwiGLU, 3 матмула) | 0.36 ms | 13 ms |
| **Сумма измеренного** | | **121 ms** |
| **Факт `fwd`** | | **245 ms** |

**Пауз между ядрами нет.** Замер CUDA-событиями вокруг префил-прохода
(`GPROF=1`, `[pf-gpu]`) даёт `blocks_gpu = 245 мс` при сумме Instant-таймеров
242 мс. То есть GPU занят всё это время, а не простаивает.

Прошлый вывод «124 мс неучтённых» был ошибкой: компонентные таймеры
(`[pfp-delta]`, `[pf-attn]`) стоят только вокруг отдельных участков и не
покрывают весь блок. Складывать их с временем блока нельзя.

`nvidia-smi` показывает среднее 78% загрузки и 8% нулевых сэмплов, но это
сэмплирование раз в 50 мс: оно ловит границы чанков (D2H логитов, снимки,
переключение на декод), а не дыры внутри чанка.

## 4. Что говорят прошлые исследования проекта

`docs/brief/research.md` (RTX 3060, sm86) — этап 2, закрыт 2026-08-25:

> Q4_K_M vs Q8_0 vs F16-сайдкар — DeltaNet proj 790/832/1105 мс. Все три формата
> упираются в одинаковый compute-потолок.
> Причинность разрыва с llama.cpp (×1.3–1.4 префилл): качество конвейера
> (host overhead, FA2 эффективность, синки) — НЕ формат весов.
> Собственные matmul-ядра = единственный рычаг.

`engine/docs/research/2026-08-13-qwen35-dense-cuda-comparison.md`:

> Chunk 2048 improves 4B throughput only 8.6% over server default 512.

Вывод для Turing: **формат весов и настройки чанка исчерпаны**. Остаётся то,
чем sm86 отличается от sm75 в нашем коде: на sm86 префилльное внимание идёт
через FA2, на sm75 — через ручной F32-матмул.

Но ручной путь стоит 12 мс из 245 (5%). Даже мгновенный FA2 даёт потолок +5%,
а нужно +10.5%. Одного FA2 недостаточно.

## 5. Открытые вопросы

1. ~~Куда уходит половина времени чанка~~ — **закрыто**: это не паузы,
   а работа ядер. `blocks_gpu` = 245 мс ≈ сумма Instant. Значит оптимизировать
   нужно сами ядра, а не отправку.
2. **Почему FA2 sm75 даёт неверный результат.** Ошибка есть уже при T=32,
   значит не маска и не длина. Кандидаты: `SmemLayoutVtransposed` при
   `kBlockN=32`, либо `Is_Q_in_regs` + `Share_Q_K_smem` на sm75.
3. **Можно ли ускорить рекуррентность DeltaNet** (31 мс, 13%).
