# Запуск Q4 MoE-модели на RTX 2080 Ti с длинным контекстом

Практическое руководство: как поднять yforge с моделью класса
Ornith-1.5-35B-Q4_K_M (41 MoE-слой, 256 экспертов, top-8) на одной
RTX 2080 Ti 11 ГиБ и получить скорость выше llama.cpp на 128k и 256k.

Проверено на стенде: RTX 2080 Ti 11 ГиБ (sm_75, CUDA 12.4, PCIe 3.0 ×16),
2× Xeon E5-2686 v4 (36 физических / 72 логических ядра), 125 ГиБ RAM.

## Что получается

| Контекст | Метрика | yforge | llama.cpp |
|---|---|---:|---:|
| 32k | decode | **33,8 t/s** | 33,3 t/s |
| 128k | prefill | **345 t/s** | 330 t/s |
| 128k | decode | **30,5 t/s** | 30,4 t/s |
| 256k | prefill | **313 t/s** | 305 t/s |
| 256k | decode | **26,8 t/s** | 26,4 t/s |

Замеры: один и тот же промпт, `temperature=0`, 64 выходных токена,
по три повтора на каждой стороне.

## Требования

- NVIDIA GPU с Turing (sm_75) или новее, 11 ГиБ VRAM.
- CUDA 12.4+ с nvcc.
- CPU: чем больше ядер, тем лучше; нужен Rayon. На стенде 28–36 потоков.
- RAM: модель + копия экспертов. Для 35B Q4_K_M это ~21 ГиБ весов и
  ~19 ГиБ RAM-копии экспертов, итого комфортно от 64 ГиБ.
- Модель в GGUF, кванты экспертов Q4_K.

## Сборка

```bash
cd engine
CARGO_TARGET_DIR=target CUDA_COMPUTE_CAP=75 \
  cargo build --release --features cuda,turing --bin yforge
```

Бинарник: `engine/target/release/yforge`. Если сборка падает на
`candle-flash-attn требует Ampere`, вы забыли фичу `turing`.

## Как узнать свой NUMA-узел

Эксперты живут в памяти одного NUMA-узла, и потоки должны работать на том
же узле, что и GPU:

```bash
nvidia-smi topo -m          # колонка NUMA Affinity
cat /sys/bus/pci/devices/<GPU>/numa_node
```

На стенде GPU на узле 1. Подставляйте свой номер в `numactl` ниже.

## Конфигурация

Создайте файл `yforge.env`:

```bash
MODEL=/models/Ornith-1.5-35B-Q4_K_M.gguf
CTX=131072
CONTEXT_LIMIT=131072
GRAPH_WINDOW=131072
SLOTS=1
API_KEYS=[{"key":"secret","name":"bench"}]
QWEN36_HOST=127.0.0.1
QWEN36_PORT=18099

GPU_ONLY=1
GPU_LAYERS=999
KV_POOL_Q8=0
PREFILL_CHUNK=2048
FLASH_ATTN=0
PGRAPH=on
MTP=0
PREFIX_CACHE_MIB=0
F16_FAST_ACC=1
PREFILL_SM75=1

MOE_CPU=1
MOE_CPU_GPU_EXPERTS=2
MOE_CPU_ASYNC=1
MOE_GPU_GRAPH=1
MOE_CPU_MAPPED=1
DECODE_GQA_MMA=1
RAYON_NUM_THREADS=28

VRAM_HEADROOM_MIB=1024
REQ_TIMEOUT=7200
```

## Запуск

```bash
numactl --cpunodebind=1 --membind=1 ./yforge --env yforge.env
```

`--cpunodebind` и `--membind` обязательны: без привязки к узлу GPU скорость
падает в 1,7 раза.

## Что включено и почему

| Переменная | Зачем |
|---|---|
| `MOE_CPU=1` | Эксперты не влезают в 11 ГиБ, они в RAM |
| `MOE_CPU_GPU_EXPERTS=2` | Оптимум: 2 эксперта считает GPU, 6 — CPU |
| `MOE_GPU_GRAPH=1` | CUDA graph подграфа MoE: без него 34 → 19 t/s |
| `MOE_CPU_ASYNC=1` | CPU-воркер перекрывается с GPU-веткой |
| `MOE_CPU_MAPPED=1` | Router и merge без D2H/H2D на слой |
| `DECODE_GQA_MMA=1` | Turing MMA в decode-attention: 2,8× на ядре |
| `RAYON_NUM_THREADS=28` | Плато 18–40; 28 даёт лучший результат |
| `PREFILL_SM75=1` | Тайловый prefill-ядро для Turing |

Keepalive Rayon-пула включён по умолчанию: фоновый пинг раз в 50 мкс не
даёт воркерам парковаться между слоями. Без него на 128k теряется 13 %.
Отключается через `MOE_KEEPALIVE=0`, период — `MOE_KEEPALIVE_US`.

## Бюджет VRAM по контексту

| Контекст | KV-пул (F16) | Остаётся VRAM |
|---|---:|---:|
| 32k | 0,6 ГиБ | ~7,5 ГиБ |
| 128k | 2,5 ГиБ | ~5,6 ГиБ |
| 256k | 5,0 ГиБ | ~3,1 ГиБ |

Если VRAM не хватает, уменьшайте `CTX` или `VRAM_HEADROOM_MIB`. Переход на
`KV_POOL_Q8=1` освобождает половину пула, но Q8-ядро на Turing медленнее
F16 (проверено: 25,1 против 27,3 t/s на 128k), поэтому по умолчанию выключен.

## Проверка скорости

В репозитории есть готовый A/B-скрипт:

```bash
MODEL=/models/Ornith-1.5-35B-Q4_K_M.gguf \
YFORGE_BIN=/path/to/yforge \
EXTRA='{"MOE_CPU_GPU_EXPERTS":"2","MOE_CPU_ASYNC":"1","MOE_GPU_GRAPH":"1","MOE_CPU_MAPPED":"1","RAYON_NUM_THREADS":"28"}' \
python3 scripts/bench/ab_llama.py yforge 131072 130000
```

Для сравнения с llama.cpp:

```bash
LLAMA_SERVER=/path/to/llama-server LLAMA_LIB_DIR=/path/to/lib \
python3 scripts/bench/ab_llama.py llama 131072 130000
```

Базовая команда llama.cpp для того же стенда:

```bash
numactl --cpunodebind=1 --membind=1 llama-server \
  -m model.gguf -c 131072 -ngl 99 -ot exps=CPU -t 36 -fa 1 \
  --host 127.0.0.1 --port 18098 -np 1 -b 2048 -ub 512
```

Оба движка запускаются отдельно: одновременно на одной карте они не
уживутся.

## Диагностика

**`cudart_static не найден`** — задайте `CUDA_PATH` на корень toolkit.

**`FlashAttention called from a cuda-turing build`** — сборка без фичи
`turing`; пересоберите с `--features cuda,turing`.

**OOM на 256k** — уменьшите `CTX`, `PREFILL_CHUNK` (например до 1024) или
поднимите `VRAM_HEADROOM_MIB`.

**Скорость упала вдвое** — проверьте, что включён `MOE_GPU_GRAPH=1` и что в
логе есть строки `[moe-graph] captured layer N`. Без графа decode 19 t/s
вместо 34.

**Скорость упала на длинном контексте** — не отключайте keepalive; именно
на 128k/256k он даёт 10–13 %.

**Проверить, что модель реально на GPU** — `nvidia-smi` во время decode
должен показывать занятую карту и 5–8 ГиБ.

## Ограничения

- Проверено на одном стенде с двумя сокетами; на одном сокете
  `RAYON_NUM_THREADS` подбирайте по числу физических ядер, а `numactl`
  можно не использовать.
- Keepalive не проверялся под конкурентной нагрузкой (несколько слотов).
- На 256k у llama.cpp разброс между прогонами достигает 17 %, поэтому
  сравнивать надо медианы нескольких прогонов, а не одиночный замер.
